# 06. 전문가 교차 검증 인터뷰 기록 (2026-09-09)

참고 템플릿 `references/ai-rag-project-docs/전문가_대화형_프로젝트_인터뷰_OpenSpec_템플릿.md`의 절차를 따라, 전문가 A(기술 아키텍트)와 전문가 B(제품·포트폴리오 심사자)가 상호 반박·수정한 기록이다. 사실은 이 날 실제로 검증한 내용만 기록하고, 결정은 사용자 확인이 필요한 항목을 명시한다.

## 프로젝트 브리프

- 프로젝트명: 산업 표면 결함 이미지 분류 (강재 데이터이므로 `반도체` 명칭 사용 금지)
- 한 줄 목표: 공개 산업(강재) 표면 결함 이미지로 재현 가능한 PyTorch 분류 실험을 수행하고, 증강 전후 비교와 추론 시간, 업로드 데모를 포트폴리오로 공개한다.
- 사용자: 컴퓨터비전·AI 모델 개발 직무 채용 담당자
- 핵심 입력: NEU-CLS(동북대학 강재 표면 결함 분류 이미지)
- 핵심 산출물: 학습·평가 결과 JSON, 비교 실험표, 추론 벤치마크, Streamlit 업로드 데모
- 제외: YOLO/세그멘테이션, 장비·PLC 연동, 현장 성능 주장, GPU/NPU 최적화 주장, MLOps

## Round 1 — 문제와 직무 적합성

**전문가 B:** 상위 폴더명은 `반도체_표면_결함_탐지_포트폴리오`인데, 사용 데이터가 강재라면 제목에 `반도체`를 쓰는 순간 포트폴리오 신뢰가 무너진다. 어떻게 고정하나?

**전문가 A:** 동의한다. 사실 검증 결과 NEU-CLS는 강재(hot-rolled steel strip) 데이터가 확실하다. 프로젝트 표기는 기존 결정대로 `산업 표면 결함 이미지 분류`로 고정하고, 폴더명은 재배포 대상이 아니므로 그대로 둔다. README 첫 문장에 "본 프로젝트는 강재 표면 결함 공개 데이터 기반이며 반도체 데이터가 아니다"를 명시한다.

**전문가 B:** `탐지`라는 단어도 위험하다. 분류(classification)를 하지 탐지(detection)를 하지 않는데 폴더명의 `탐지`를 문서에 끌어오면 요구사항 오해를 낳는다.

**결정 기록:** 문서·README·데모 전체에서 과제명은 `분류`로만 표기한다. `탐지`·`검출`은 YOLO/바운딩 박스 문맥에서만 쓰며, 본 프로젝트에는 쓰지 않는다. (사용자 확인 대기)

## Round 2 — 데이터와 안전성

**전문가 A:** 데이터 권리는 두 축이다. (1) 학술 연구 전용·상업 이용 불가 — 포트폴리오(비영리 학습 목적)는 적합하지만 상업 서비스·유료 강의 자료화는 금지다. (2) 원본 재배포 금지 — 원본을 Git에 넣지 않고 `data/`를 `.gitignore` 처리한다.

**전문가 B:** 문제는 획득 경로다. 공식 페이지가 봇 차단 중이어서 내가 자동으로 받을 수 없음이 확인됐다. 여기서 세 가지 현실적 경로가 있다.

1. 사용자가 브라우저로 공식 페이지에 접속해 NEU-CLS(Google Drive)를 직접 내려받는다 — 출처 가장 공식적.
2. Kaggle 계정 API 토큰을 제공받아 `kaustubhdikshit/neu-surface-defect-database` 미러를 내려받는다 — 자동화 가능, 단 train/val 사전 분할 버전이라 본 프로젝트의 자체 분할 원칙과 충돌할 수 있어 원본 이미지 폴더만 취급 필요.
3. GitHub/기타 미러를 계속 탐색한다 — 가용성이 불확실하고 검증 부담이 가장 크다.

**전문가 A:** 어떤 경로든 수신 후 다음 네 가지 정합성 검사를 통과해야 채택한다: 총 파일 수 1,800, 클래스당 300, 이미지 크기 200×200, JPEG 디코딩 성공. 실패하면 해당 경로를 기각하고 기록으로 남긴다.

**결정 기록:** 획득 경로는 사용자 결정 대기(옵션 1/2/3). 채택 여부와 무관하게 `docs/data-governance.md`에 출처·날짜·SHA-256·검사 결과를 기록한다.

## Round 3 — 시스템 설계와 대안

**전문가 B:** RTX 3070이 있는데 torch가 CPU-only로 설치돼 있다. CPU로 진행할 이유가 있나? 있다면 면접에서 "GPU가 있는데 왜 안 썼나"라는 질문을 감수해야 한다.

**전문가 A:** 감수할 필요가 없다. CUDA 빌드 torch로 재설치하면 8GB VRAM에서 ResNet18(200×200, batch 32) 학습이 충분히 가능하다. 대신 단일 이미지 추론 벤치마크는 CPU와 GPU를 **같은 환경에서 각각** 측정해 함께 기록하는 편이 포트폴리오 가치가 더 크다(배포 대상 환경은 CPU인 경우가 많다는 논거가 생김). 리스크는 CUDA torch 재설치가 기존 설치를 바꾸는 것뿐이며, 버전·CUDA 표기는 문서에 고정한다.

**전문가 B:** 재설치 실패 가능성도 원장에 남겨라. CPU-only가 폴백이며, 그 경우 학습 시간이 늘지만(1,800장 기준) 진행 불가는 아니라는 점도.

**전문가 A:** 모델 선택 재확인: 1,800장 스크래치 학습은 과적합 위험이 커서 ImageNet 전이학습이 적합하다. ResNet18이 2주 범위와 재현성에 적합하다는 기존 결정을 유지한다. torchvision 사전학습 가중치는 첫 실행 시 인터넷 다운로드가 필요하므로 README에 명시한다.

**결정 기록:** GPU 사용(CUDA torch 재설치)을 권장안으로 제안 — 사용자 결정 대기. 폴백은 기존 CPU-only torch.

## Round 4 — 품질·실패·평가

**전문가 A:** 1,800장에서 test 300장(클래스당 50)이면 한 장 차이가 지표 0.3%p 움직인다. 고정 seed(42)·고정 분할·동일 test set 원칙은 필수고, 같은 설정 재실행 결과 일치 여부를 확인해야 한다.

**전문가 B:** Accuracy 단독 보고 금지 원칙은 유지한다. macro F1 + 클래스별 P/R/F1 + confusion matrix를 메인으로, "증강이 개선되지 않으면 그 사실을 그대로 공개"하는 계약도 유지한다. 6클래스 균형 데이터임을 EDA에서 증명하면 클래스 가중치 논쟁을 예방할 수 있다.

**전문가 A:** 신뢰도 임계값은 validation 분포를 본 뒤에만 확정하고, 그 근거를 문서에 남긴다(초기값 0.60은 임시).

**결정 기록:** 기존 품질 결정 유지 + seed 고정 재실행 검증 항목 추가.

## 실행시간 교차 검증 — 데이터 수신·Phase 1 (2026-09-09)

**전문가 A:** 사용자가 준 파일은 zip이 아니라 `NEU-CLS.rar`였다. 파일명도 `Cr_1.bmp`식 약어 접두사라 기존 파서를 그대로 쓰면 전부 기각된다. 약어 매핑(Cr/In/Pa/PS/RS/Sc)은 NEU 공식 표기이므로 코드에 명시적으로 두고 테스트로 고정해야 한다.

**전문가 B:** 수집 스크립트가 0건을 조용히 통과시켰던 첫 실행은 결함이었다. RAR 지원(7-Zip)을 추가하고, 실패 시 명확한 오류를 내도록 고쳤다.

**결정·검증:** RAR 지원 추가 + 약어 매핑 명시 후 재실행: 1,800장 전부 디코딩 성공, 200×200, 6클래스×300 정확 일치, 손상 0건. RAR SHA-256 `A85BCC6B…AA96F8`를 거버넌스에 기록했다.

## P0 교차 검증 — 중복 파일 누수 (2026-09-09)

**전문가 A:** 정합성 검사에서 SHA-256 완전 중복 1쌍(`Pa_101.bmp` = `Pa_105.bmp`)이 발견됐고, 초기 seed=42 분할에서 둘이 train/val에 갈라져 배정됐다. 이는 문자 그대로의 train-val 누수이며 val 지표(=모델 선택 기준)를 오염시킨다.

### #13 — benchmark canonical 덮어쓰기 방지

**전문가 A:** 기본 `--out`은 checkpoint 폴더의 `benchmark.json`을 무조건 덮어쓴다. 이미 발생한 산출물 손실 사건의 재발을 코드로 막는다: 대상 파일이 존재하는데 `--force`도 `--out`도 없으면 실행을 중단하고 안내한다. 판정 로직은 순수 함수로 만들어 테스트한다.

**전문가 B:** 첫 실행(파일 없음)은 명령이 바뀌지 않아야 한다. 기존 README 명령 호환성을 유지하되, 갱신 시 `--force`가 필요해졌음을 문서에 명시한다.

### #12 — 확률 보정(temperature scaling) 실험

**전문가 A:** 온도 스케일링은 파라미터 하나(T)를 val NLL 최소화로 맞추는 표준 보정법이다. val 로짓에 대해 결정론적 격자 탐색(0.5~5.0)으로 T를 구하고, `predict`에 `temperature` 인자를 추가해 데모에서도 사용 가능하게 한다. T=1.0이 기본이므로 기존 동작은 불변이다.

**전문가 B:** "보정했으니 개선됐다"를 미리 가정하지 않는다. 판정 기준: (1) val NLL이 실제로 감소하는가, (2) OOD 스캔에서 변형 상황의 신뢰도가 정확도에 가까워지는가(과신 완화), (3) 0.60 미만 플래그 수가 늘어나는가. 개선이 없으면 그대로 기록하고 기본값을 바꾸지 않는다.

**결정:** `scripts/calibrate_temperature.py`(결정론적 격자 탐색, 결과 JSON 저장) + `predict(temperature=)` + `ood_scan.py --temperature` 옵션. T=1.0 대비 NLL·OOD 지표 비교를 문서화.

### #11 — 입력 품질 게이트 (OOD 과신의 실질 보완)

**전문가 A:** 과신 특성상 신뢰도 임계값만으로는 훼손 입력을 못 걸러낸다. 이미지 자체의 정량 품질 지표를 선검사하는 게이트를 둔다: (1) 라플라시안 분산(선명도/블러), (2) 중앙값 절대편차 기반 노이즈 추정(Donoho 추정량), (3) 평균 밝기. 지표 함수는 순수 함수로 테스트한다.

**전문가 B:** 임계값을 임의로 정하면 또 "근거 없는 상수"가 된다. 절차를 고정한다: clean val 270장에서 지표 분포를 측정하고, clean 데이터가 통과하는 선(예: sharpness p5, noise p95)을 기준으로 변형 데이터(σ30·r3 등)에서 실제로 걸러지는지 검증한 뒤에만 상수로 확정한다. 기각되면 그 사실도 기록한다.

**결정:** `src/defect_cls/quality.py`(지표·판정 순수 함수) + `scripts/quality_gate_calibration.py`(분포 측정·임계값 근거 산출) + 데모 연동(품질 미달 시 경고 표시). 임계값은 측정 근거를 기록한 뒤 확정.

## 후속 교차 검증 — 벤치마크 실행 계약 (2026-09-09)

**기술 아키텍트:** 벤치마크가 `--devices cuda`를 CUDA 미가용 환경에서 요청하거나 오타 난 장치를 받으면 측정 대상이 빈 배열인 JSON을 성공으로 저장할 수 있었다. `--iters 0`도 통계 계산 단계까지 진행해 입력 계약이 불명확했다. 이는 측정값의 신뢰성과 실패 가시성을 해친다.

**포트폴리오 심사자:** 빈 산출물을 성공처럼 남기면 실제 지연시간을 측정했다는 주장과 산출물의 내용이 어긋난다. 장치·반복 수 계약을 명시적으로 실패시키고 자동 테스트로 고정해야 한다. 이 변경은 기존 실측 수치·다중-seed 실험을 생성하거나 변경하지 않는다.

**결정·구현:** `resolve_benchmark_devices()`가 빈 목록·알 수 없는 장치·CUDA 미가용 요청을 거부하고, CLI가 warm-up은 0 이상·반복 수는 1 이상만 받도록 했다. 정상 CPU 요청은 그대로 허용한다. README에는 사용 가능한 `cpu`/`cuda`만 지정한다는 조건을 추가했다.

**검증 기준:** CPU 장치 해석 성공, 빈/미가용 CUDA/알 수 없는 장치 거부, 전체 pytest 통과. 합성 fixture만 사용하며 학습·평가·다중-seed 수치를 새로 산출하지 않는다.
